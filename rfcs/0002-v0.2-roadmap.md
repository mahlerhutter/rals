# RFC-0002: RALS v0.2 Roadmap — Learnings from v0.1 Reference Implementations

**Status:** Draft for Discussion
**Type:** Major Version Planning
**Authors:** Manuel Mendel (Editor)
**Created:** 2026-05-15
**Targets:** RALS v0.2 (Q4 2026 working draft, Q2 2027 publication target)
**Supersedes:** None
**Superseded by:** None

---

## Abstract

This RFC consolidates structural learnings from six reference implementations of RALS v0.1 — operating PV (Spain), operating wind with EEG market-premium support (Germany), ready-to-build BESS with stacked revenues (UK), operating run-of-river hydro in an emerging-market jurisdiction (Vietnam), operating triple-hybrid PV+wind+BESS with mining offtaker (Chile), and late-stage development PV (Poland). The reference implementations exposed eight categories of structural gap in v0.1 that cannot be resolved by clarifying language alone and require schema changes for v0.2.

This RFC enumerates those gaps, proposes resolution approaches, identifies the trade-offs each resolution imposes, and lists the open questions for community input before v0.2 schema work begins. It does not itself propose final schema syntax; that follows in subsequent technology-specific and topic-specific RFCs once the v0.2 direction is endorsed.

---

## 1. Status of this Document

This is a draft RFC posted for community review. It will remain open for comment for three months from the date above (through 2026-08-15) before being moved to "Final Comment Period" status. Implementers and prospective implementers are explicitly invited to push back on any of the proposed directions; the goal of this RFC is to surface disagreement before v0.2 schema work begins, not to ratify a fait accompli.

The RFC is structured as a series of Issues. Each Issue carries the same internal format: Observation, v0.1 Behavior, Proposed v0.2 Resolution, Trade-offs, Alternatives Considered, Open Questions.

## 2. Background

RALS v0.1 was published as a Working Draft on 2026-05-15 alongside six reference implementations of intentionally varied characteristics:

| Project | Technology | Lifecycle | Country | Designed to stress |
|---|---|---|---|---|
| Helios | Solar PV | Operating | ES | Baseline EU mature asset |
| Aeolus | Onshore Wind | Operating | DE | EEG complexity, repowering optionality |
| Prometheus | BESS | Ready-to-Build | GB | Capacity Market, stacked revenues |
| Mekong | Hydro RoR | Operating | VN | Emerging markets, FX, resettlement |
| Atacama | PV+Wind+BESS Hybrid | Operating | CL | Triple-hybrid, mining offtaker, nodal pricing |
| Wisła | Solar PV | Development | PL | Late-stage development, optionality, milestones |

The reference implementations were not produced by independent third parties; they were produced by the editor as a structured stress-test of the v0.1 schema. This is methodologically weaker than independent implementations and is acknowledged as a limitation: the editor's own implementations cannot reliably surface gaps the editor's own mental model has already accommodated. External implementer feedback during the comment period is therefore particularly important for this RFC.

That said, six implementations spanning four technologies, three lifecycle stages, and six regulatory jurisdictions exposed gaps that the editor did not anticipate when writing v0.1. The eight Issues in Section 3 are those gaps.

## 3. Issues

### Issue 3.1 — `operating_history` is conceptually wrong for non-operating assets

**Observation.** v0.1 designates `operating_history` as one of seven required top-level sections and marks all fields REQUIRED conditional on the lifecycle stage. In practice, two of the six reference implementations (Prometheus, RTB; Wisła, development) cannot populate this section in any meaningful way. The two implementations worked around it differently: Prometheus marked the section `applicable: false` and cross-referenced `process.construction_milestones`; Wisła omitted the section entirely. Both workarounds are a code smell indicating the section does not belong in the data model for these assets.

The deeper problem is that Greenfield and Development assets have a structurally different value driver — *unresolved milestones with probabilistic completion* — that has no equivalent in operating assets and no place to live in v0.1. The Wisła implementation invented a `development_milestone_tracker` top-level section out-of-spec to carry this information. This is functional but undermines the standard.

**v0.1 Behavior.** Section 11 is `operating_history`, required for assets in lifecycle stages `operating`, `commissioning`, `repowering_candidate`, and optional otherwise. No equivalent section exists for development-stage milestone tracking.

**Proposed v0.2 Resolution.** Replace `operating_history` with a polymorphic Section 11 whose schema varies by lifecycle stage:

```
section_11 := operating_history     if lifecycle_stage in [operating, commissioning, repowering_candidate]
            | construction_tracker   if lifecycle_stage in [under_construction, ready_to_build]
            | development_tracker    if lifecycle_stage in [greenfield, development]
            | decommissioning_status if lifecycle_stage = decommissioning
```

Each variant uses its own field schema appropriate to the stage. JSON Schema conditionalSchema (if/then/else) supports this pattern; the trade-off is that simple validators may not handle conditional schemas correctly.

**Trade-offs.**
- Pro: Each stage gets purpose-fit fields; no nonsense fields like "operating history of an unbuilt asset"
- Pro: Buyer agents can reliably parse milestone trackers without inferring from absence
- Con: Polymorphism complicates parsers; some implementers may simply omit the section
- Con: Lifecycle transitions (development → RTB → operating) require document rewrites, not field edits

**Alternatives Considered.**
- *Keep `operating_history` as universal section with empty arrays* — what v0.1 does. Rejected because the missing-data semantic is unclear (no data because no history yet, or no data because seller hasn't filled it in?).
- *Make Section 11 entirely optional* — loses required-tracking discipline for ops assets.
- *Add `development_milestone_tracker` as an eighth top-level section* — bloats the schema with a section that is empty for every operating asset, while `operating_history` stays empty for every development asset.

**Open Questions.**
- Should `repowering_candidate` use operating_history (since the asset is operating) or a hybrid tracker capturing both ops history and repowering planning milestones? Two of six implementations are silent on this.
- How should buyers query an asset whose lifecycle stage may transition during the M&A process (e.g., RTB asset closing as Operating)? The document version at signing differs from version at closing.

### Issue 3.2 — Hybrid assets need formal multi-technology sub-blocks

**Observation.** The Atacama implementation modeled a triple-hybrid (PV + Wind + BESS) behind a single grid connection. v0.1's `technical` section is implicitly mono-technology — the field set assumes one production curve, one resource assessment, one equipment generation. The Atacama implementation worked around this by inventing per-technology sub-blocks (`technical.pv`, `technical.wind`, `technical.bess`) plus an `integration` sub-block plus `shared_infrastructure`. This pattern produced a clean, parseable document but is entirely out-of-spec.

Hybrid asset prevalence is increasing — Chile, ERCOT, Australia, parts of EU — and 2-of-3 future M&A transactions involving storage will likely involve hybrid configurations. v0.1's silence on this is a structural omission, not a stylistic one.

**v0.1 Behavior.** `asset_type: hybrid` is an enum value but no schema scaffolding tells implementers what fields apply.

**Proposed v0.2 Resolution.** Introduce formal multi-technology sub-block structure:

```
technical:
  asset_type: hybrid
  subblocks:
    - id: pv-01
      technology: solar_pv
      <full PV technical schema>
    - id: wind-01
      technology: onshore_wind
      <full wind technical schema>
    - id: bess-01
      technology: bess
      <full BESS technical schema>
  integration:
    topology: ac_coupled | dc_coupled | hybrid_coupled
    ems_co_optimization: true
    grid_forming_at_poc: true
    shared_infrastructure: { ... }
```

Each subblock validates against its technology-specific schema extension. The `integration` block carries fields that exist *only* for hybrid assets: coupling topology, EMS co-optimization scope, grid-forming designation, shared infrastructure.

**Trade-offs.**
- Pro: Buyer agents can mechanically iterate subblocks
- Pro: Each technology's mature schema (developed for mono-technology assets) is reused without duplication
- Con: File size grows substantially for hybrids
- Con: Some shared design parameters (commissioning date, expected lifetime) need to be expressed at both top-level and subblock level — risk of inconsistency

**Alternatives Considered.**
- *Multi-document approach* — one RALS file per technology, linked via `parent_asset_id`. Rejected because it fragments the transaction; an M&A buyer is buying the integrated asset, not the constituent technologies.
- *Flat schema with technology-prefixed fields* — `pv_capacity_mw`, `wind_capacity_mw`, `bess_power_mw`. Rejected because it doesn't scale (some hybrids have multiple instances of the same technology) and obscures the integration story.

**Open Questions.**
- How should production estimates aggregate across subblocks? Atacama declared per-subblock P50/P75/P90 plus a combined modeled-output, but the combined number depends on EMS dispatch logic and is not deterministic from the subblock numbers.
- For curtailment allocation between subblocks (Atacama declared PV is curtailed first), should the spec mandate allocation methodology or leave it to seller disclosure?

### Issue 3.3 — Nodal/zonal pricing markets require structured fields

**Observation.** The Atacama implementation (Chilean nodal market) needed to convey severe sun-hour-to-evening-peak price differentials at a specific market node — average $28/MWh masking 32% of hours below $5/MWh and evening peaks of $78/MWh. Without this granularity, no buyer can model the BESS arbitrage opportunity or assess curtailment risk. v0.1 has no structured field for this; the Atacama implementation embedded a free-form `historical_nodal_marginal_cost_2025` object inside `grid_connection`.

Nodal and zonal pricing applies to Chile, the US PJM/ERCOT/CAISO/MISO/SPP/NYISO markets, the Irish SEM, the Australian NEM, parts of the Nordic SE/NO/DK/FI zonal system, and emerging Polish markets. The number of jurisdictions where this matters will increase as more EU markets move toward locational marginal pricing.

**v0.1 Behavior.** No field exists. Implementers improvise.

**Proposed v0.2 Resolution.** Add an optional structured block to `grid_offtake`:

```
locational_pricing:
  market_type: nodal | zonal | uniform
  pricing_node_id: "Antofagasta-Norte_220"
  pricing_node_description: "..."
  historical_price_distribution:
    period_start: "2023-01-01"
    period_end: "2025-12-31"
    granularity: hourly
    average_price_local_currency_mwh: 28
    percentiles:
      p10: 2
      p25: 6
      p50: 18
      p75: 42
      p90: 68
      p95: 95
      p99: 145
    diurnal_summary:
      sun_hours_avg: 8
      evening_peak_avg: 78
    zero_or_negative_pricing_pct: 18
    detail_url: "..."
    detail_access: nda_required
```

This structure scales from simple (one summary number for uniform-priced markets) to rich (full hourly distribution with detail URL pointer for nodal markets).

**Trade-offs.**
- Pro: Buyer agents can quantify revenue volatility without manually parsing prose
- Pro: Comparable across markets (P50 in Chile maps to P50 in ERCOT)
- Con: For uniform-priced markets the structure is mostly empty
- Con: Historical price data may itself be tier-`nda_required` (commercial sensitivity)

**Alternatives Considered.**
- *Free-form prose field* — what most assets currently do in IMs. Rejected because it's not machine-parseable.
- *Mandate detail URL only* — forces external data dependency. Rejected because the summary statistics are themselves valuable.

**Open Questions.**
- Should the spec adopt a canonical reference period (e.g., trailing 24 months) or allow seller-defined periods? Canonical is comparable, seller-defined is realistic.
- Should we mandate hourly granularity or allow weekly/monthly summaries for less mature markets?

### Issue 3.4 — Capacity Market and other regulatory programs are not contracts

**Observation.** Both Prometheus (UK Capacity Market) and Atacama (Chile DS 70/2023 Capacity Payments) participate in regulator-administered capacity payment programs. v0.1 modeled these as entries in `offtake_contracts`, but this is conceptually wrong: they are not contracts negotiated bilaterally between seller and buyer; they are regulated programs the asset is enrolled in.

The mis-modeling has practical consequences. Contract fields like `change_of_control_clause` and `counterparty_credit_rating` apply differently to a regulated program than to a bilateral PPA. The Prometheus implementation worked around this with notes; the Atacama implementation introduced an out-of-spec `capacity_payment_program` block within `grid_offtake`.

**v0.1 Behavior.** Capacity markets and similar regulated programs squeezed into `offtake_contracts` array.

**Proposed v0.2 Resolution.** Introduce a separate `regulated_revenue_programs` block within `grid_offtake`, parallel to `offtake_contracts`:

```
grid_offtake:
  offtake_contracts: [ ... ]           # bilateral commercial arrangements
  regulated_revenue_programs: [ ... ]  # regulator-administered programs
  merchant_revenue_streams: [ ... ]    # uncontracted exposure
```

Each `regulated_revenue_programs` entry has its own field set: program identifier, regulator, derating methodology (where applicable), award basis, indexation, change-of-ownership notification (not consent), program-specific performance obligations.

**Trade-offs.**
- Pro: Conceptually clean separation
- Pro: Buyer agents can model regulated vs. bilateral revenue streams with different risk treatments
- Pro: Spec can evolve regulator-program rules (DS 70 derating, UK CM derating methodology, Italian capacity market) without disturbing contract schemas
- Con: One more top-level field within `grid_offtake`
- Con: Edge cases (a regulated support scheme that *is* delivered through a contract, like the German EEG gleitende Marktprämie) require judgment — see Open Questions

**Alternatives Considered.**
- *Tag contracts with a `regulation_type` enum* — keeps single array but introduces conditional field rules within a single object type. Rejected for parser complexity.
- *Force everything into `offtake_contracts` with documentation* — what v0.1 does. Already shown insufficient.

**Open Questions.**
- Where does German EEG Marktprämie fit? It is regulated (anzulegender Wert set by auction or formula) but operates through a Direktvermarkter who has a commercial contract with the asset. The Aeolus implementation treated it as a contract; that may have been wrong.
- Where do Italian Conto Energia legacy FITs fit?

### Issue 3.5 — Connection process has more states than `connected: true/false`

**Observation.** The Wisła implementation revealed that Polish solar development has at least three distinguishable connection states with materially different value implications: connection application filed, Connection Conditions issued (Warunki Przyłączenia, 2-year validity, ~80% probability of progressing to Agreement), Connection Agreement executed (Umowa Przyłączeniowa, locks in capacity and timeline). This is not Polish exceptionalism — Spain has `Permiso de Acceso` vs `Permiso de Conexión`, Italy has STMG (Soluzione Tecnica Minima Generale) vs Connection Contract, Germany has Netzanschlusszusage stages, Chile has the queue management milestone system. The value implications are substantial: an asset with Connection Conditions only might be worth €170k/MWp; with Connection Agreement executed, €240k/MWp; an additional risk-discount applies if the Connection Conditions are within 6 months of expiry.

v0.1 defines no connection-process-state field at all. The Prometheus implementation improvised a `connection_capacity_secured: boolean`; even as an improvisation, a binary flag is far too coarse to carry the value distinctions above.

**v0.1 Behavior.** No connection-process-state field. `grid_connection` carries `connection_capacity_mw` and `connection_agreement_date`, from which connection status can only be inferred. Implementers improvise inconsistently — Prometheus used a binary `connection_capacity_secured` boolean; other implementations carry implicit milestone dates instead.

**Proposed v0.2 Resolution.** Replace binary field with a structured connection state object:

```
grid_connection:
  state: applied | initial_offer_received | conditions_issued | agreement_executed | energization_complete | derated | terminated
  state_history:
    - state: conditions_issued
      date: "2024-08-30"
      reference: "WP-2024-PLE-082"
    - state: agreement_executed
      date: "2026-07-31"  # if applicable
  state_validity:
    current_state_valid_until: "2026-08-30"  # for time-limited states like Conditions
    renewal_requires_reapplication: true
```

State enum values are normative; each jurisdiction's specific terminology (Warunki Przyłączenia, Permiso de Acceso, STMG) maps to one of these canonical states via the country-specific compliance annex.

**Trade-offs.**
- Pro: Buyer agents can compare assets across jurisdictions on the same axis
- Pro: Time-limited states are surfaced explicitly (Wisła's most material risk)
- Con: Mapping jurisdiction-specific stages to canonical states will be contested; some stages don't cleanly map
- Con: State enum will likely need v0.3 additions as more jurisdictions are modeled

**Alternatives Considered.**
- *Jurisdiction-specific connection fields* — `grid_connection.poland.warunki_przylaczenia_status`. Rejected: explodes the schema and prevents cross-market comparison.
- *Free-form `connection_milestones` array* — allows arbitrary state names. Rejected: defeats the comparability purpose.

**Open Questions.**
- Should the canonical state set be richer (10+ states) to accommodate fine-grained jurisdictional distinctions, or leaner (5-6 states) to ensure comparability?
- How do we handle the chain of connection rights for hybrid or expanded assets where parts of the project are in different states?

### Issue 3.6 — Greenfield assets need probabilistic and risk fields

**Observation.** The Wisła implementation's `development_milestone_tracker` populated each outstanding milestone with `probability_pct_estimated` and `value_at_stake_eur` fields, plus a separate `risk_register_summary` with residual risk levels and impact magnitudes. None of this is in v0.1. Yet none of it is optional in practice: any rational buyer of a development asset is computing risk-adjusted NPV by weighting milestone-conditional payoffs by their probability. If the spec doesn't carry this information, buyers extract it from the data room manually, defeating the spec's purpose.

The issue is not unique to greenfield. Operating assets have residual risks too (regulatory, counterparty, climate). But for greenfield, risk *is* the asset — it's the dominant value driver, not a footnote.

**v0.1 Behavior.** No structured probabilistic or risk fields.

**Proposed v0.2 Resolution.** Add optional `risk_quantification` blocks at multiple levels:

```
# Within development_milestone_tracker (greenfield/development assets):
outstanding_milestones:
  - milestone: "..."
    probability_pct_estimated: 80
    probability_basis: "..."
    value_at_stake_currency_amount: 22_400_000
    value_at_stake_methodology: "..."

# At compliance level (any asset stage):
risk_register:
  - risk: "..."
    likelihood: low | medium | high | very_high
    impact: low | medium | high | very_high
    residual_risk: low | medium | high | very_high
    mitigation_status: in_place | planned | not_applicable
    value_at_stake_currency_amount: ...

# Optional but strongly recommended for development-stage assets.
```

Probability estimates carry an explicit `probability_basis` field (sponsor estimate vs. third-party assessor vs. statistical reference class) to avoid false precision.

**Trade-offs.**
- Pro: Buyer agents can compute risk-adjusted valuations directly
- Pro: Different assets become comparable on risk dimensions
- Con: Probability estimates are inherently subjective; standardization may create false precision
- Con: Sellers may decline to publish quantified risk assessments for liability reasons

**Alternatives Considered.**
- *Qualitative only (low/medium/high)* — what most IMs do. Loses comparability and quantification.
- *Mandate Monte Carlo simulation output* — most sellers can't produce this. Rejected as overreach.

**Open Questions.**
- Should the spec require a third-party probabilistic assessment for greenfield assets above some size threshold, or remain seller-disclosed?
- How should buyer agents weight seller-estimated probabilities vs. third-party-estimated probabilities? This is a question for buyer-agent implementation guidance, not the spec itself, but the spec should make the distinction parseable.

### Issue 3.7 — Multi-currency assets need explicit FX modeling

**Observation.** Three of six reference implementations involve material currency exposure:
- Mekong: USD reporting, VND functional, VND PPA, USD debt
- Atacama: USD reporting, USD functional, USD PPA, USD debt, but ~35% CLP-denominated OPEX
- Wisła: PLN reporting, PLN functional, EUR secondary reporting, capex in PLN with EUR-denominated module pricing exposure

v0.1 has `reporting_currency` as a single ISO 4217 code and implicitly assumes single-currency operation. This is wrong for the majority of emerging-market assets and for many European assets with cross-border supplier exposure.

**v0.1 Behavior.** `reporting_currency: EUR` (single field).

**Proposed v0.2 Resolution.** Replace with a structured `currency_profile`:

```
currency_profile:
  reporting_currency: USD
  functional_currency: VND
  reporting_basis_for_fx: "average rate for income statement, closing rate for balance sheet"
  revenue_currencies:
    - currency: VND
      pct_of_total: 100
  cost_currencies:
    - currency: VND
      pct_of_total: 78
    - currency: USD
      pct_of_total: 22
  debt_currencies:
    - currency: USD
      pct_of_total: 100
  fx_assumption_basis_date: "2026-04-30"
  fx_assumptions:
    - currency_pair: USD/VND
      rate: 25750
  fx_risk_management:
    natural_hedge_assessment: "limited — USD debt vs VND revenue mismatch"
    hedging_instruments: "none / forward / swap / options"
    hedged_pct: 0
```

**Trade-offs.**
- Pro: Currency exposure becomes structured, comparable across emerging-market assets
- Pro: FX risk is surfaced explicitly rather than hidden in narrative
- Con: Substantially more fields for single-currency assets where most are trivially populated
- Con: Sellers may not have done the breakdown analysis; spec is asking for work

**Alternatives Considered.**
- *Reporting-currency-only with optional `material_fx_exposures` notes* — keeps single-currency assets simple but loses structure for multi-currency.
- *Force FX modeling only for assets above a threshold* — arbitrary.

**Open Questions.**
- Should `fx_assumptions` be required, or should it default to "spot at basis date"? Spot rates can mislead for long-dated assets.
- Should hedging-instrument detail be required tier `nda_required` or `final_shortlist`?

### Issue 3.8 — Jurisdiction-specific compliance is becoming unmanageable

**Observation.** Reference implementations introduced jurisdiction-specific compliance blocks ad hoc:
- Vietnam: `vietnam_specific_compliance` (MOIT licenses, DPPA registration, NSMO status)
- Chile: `chile_specific_compliance` (CEN registration, DS 70 status, DS 125/88 reform exposure)
- UK: `uk_specific_compliance` (Ofgem licence, BM unit, Elexon signup)
- Poland: `poland_specific_compliance` (RES Act eligibility, CfD status, land-use restrictions)

Each block is structurally similar but field-set differs. v0.1 does not formalize the jurisdiction-compliance container; each implementation makes one up.

This is unsustainable: extending RALS to additional jurisdictions (Brazil, India, Australia, South Africa, ASEAN markets, MENA) without a canonical container will fragment the schema.

**v0.1 Behavior.** Ad-hoc per-jurisdiction blocks invented by implementers.

**Proposed v0.2 Resolution.** Introduce canonical `jurisdiction_specific_compliance` array at the compliance section level:

```
compliance:
  jurisdictions:
    - country: VN
      compliance_items:
        - item: moit_electricity_operation_license
          status: active
          reference: "EOL-2018-MOIT-0142"
          valid_until: "2028-05-30"
        - item: dppa_eligibility_decree_57_2025
          status: eligible
          notes: "..."
    - country: CL
      compliance_items:
        - item: cen_market_participant_registration
          status: registered
        - item: ds_70_2023_capacity_program
          status: active_participant
```

The `item` field values are drawn from a per-country canonical list maintained in `docs/compliance/<country>.md`. New countries get their canonical list added via RFC. Items have type-checked enums for status fields.

**Trade-offs.**
- Pro: Buyer agents can mechanically query jurisdiction-specific compliance across assets
- Pro: Adding a new country becomes a documented RFC process, not an ad-hoc extension
- Pro: ESG-fund reporting (SFDR, TCFD) can pull jurisdiction-specific items reliably
- Con: Spec maintenance burden — keeping per-country item lists current as regulations evolve
- Con: Multi-jurisdiction assets (cross-border transmission, EU CBAM cross-references) need careful handling

**Alternatives Considered.**
- *Leave as free-form per-implementation* — what v0.1 effectively does. Already shown insufficient.
- *Single global compliance enum* — explodes to unmanageable size, doesn't reflect that "valid MOIT license" only matters in Vietnam.

**Open Questions.**
- Who maintains the per-country canonical item lists? Editor alone is unsustainable; should there be country-specific stewards in the governance model?
- How are deprecated items handled? When Vietnamese Decree 80/2024 was superseded by Decree 57/2025, what happens to assets that referenced Decree 80 items?

## 4. Out-of-Scope for v0.2

The following are recognized as gaps but deferred to v0.3 or later:

- **Multi-document portfolio aggregation.** How a portfolio RALS file references its constituent single-asset RALS files. Deferred because portfolio M&A practice is less standardized than single-asset; canonical patterns not yet apparent.
- **Q&A protocol.** A structured replacement for email-based seller-buyer Q&A during diligence. Deferred because tooling for this is genuinely speculative; no existing convention to standardize.
- **Comparable transaction references.** Optional fields linking to anonymized closed comparables. Deferred because anonymization standards are unclear and reference data may not be available.
- **Repowering optionality.** Dedicated subschema for repowering candidates. Deferred because the Aeolus implementation showed this can be carried in v0.2 as a sub-section of `technical` rather than a top-level concept.
- **JWS document signing.** Was mentioned as v0.2 candidate; on reflection, the security model needs more design work and broader implementer feedback before specifying. Deferred to v0.3.
- **Comprehensive ESG/CSRD-ESRS-aligned reporting fields.** Currently held minimal in `compliance.esg`. Full CSRD alignment is a v1.x project; v0.2 will continue with minimal ESG.

## 5. Process and Timeline

This RFC's comment period runs through 2026-08-15.

Following the comment period, each Issue (3.1 through 3.8) is expected to produce a child RFC with concrete schema proposals. Child RFCs targeted for completion by 2026-Q4. v0.2 working draft target publication 2027-Q1. v0.2 publication target 2027-Q2.

The editor commits to a public response to every substantive comment received during the comment period, even if the response is "this point is acknowledged but the proposed direction will not change."

If during the comment period it becomes clear that consensus on any Issue cannot be reached, that Issue will be deferred to v0.3 rather than rushed into v0.2. The standard's credibility depends more on getting fewer things right than on shipping more things.
